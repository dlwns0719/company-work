# 업무·사고 성향 진단 — 재실행용 프롬프트

주기적으로 자기 업무 방식을 대화 기록 기반으로 재점검하기 위한 문서다.
결과는 `work-style/YYYY-MM-DD.md` 로 누적한다.

---

## 1. 언제 돌리나

- 분기 1회, 또는 팀원·상사에게 업무 방식에 대한 피드백을 받았을 때
- 직전 회차 이후 대화 기록이 최소 1,000 발화 이상 쌓였을 때
- 직전 회차의 개입 항목을 실제로 적용한 뒤 효과를 보고 싶을 때

너무 자주 돌리면 표본이 겹쳐 변화를 못 본다. 최소 6주 간격을 둔다.

---

## 2. 실행 절차

### 2.1 코퍼스 추출

이 컴퓨터의 전체 세션 로그에서 **사용자 발화만** 뽑는다. 어시스턴트 출력은 증거가 아니다.
다만 사용자가 어시스턴트 결과에 어떻게 반응했는지는 증거가 된다.

```bash
# 세션 로그 위치
ls ~/.claude/projects/*/*.jsonl

# 추출 대상: type == "user" 이면서 tool_result 가 아닌 text 블록
# 제외: system-reminder, task-notification, 세션 요약, hook 출력, 슬래시 커맨드 확장분
```

추출 결과는 세션별 텍스트 파일로 떨어뜨리고, 각 발화에 `[턴번호] 타임스탬프` 를 붙인다.
인용 시 이 번호를 근거로 쓴다.

주의: 세션 재개 시 동일 발화가 재기록되는 경우가 있다. 2026-08-31 회차에서는
가장 큰 세션 하나에 중복 127건(빈도 약 6% 부풀림)이 있었다. 빈도 수치를 쓸 때 중복 제거 여부를 밝힌다.

### 2.2 정량 측정

해석 전에 셀 수 있는 것을 먼저 센다. 최소 항목은 아래와 같다.

- 발화 길이 분포(중앙값·p90), 짧은 반응형 비율, 긴 지시형 비율
- 어휘 범주별 발화 수: 넓이 요구 · 깊이 요구 · 중간구조 만들기 · 범위 축소/정지 · 파킹 · 복귀 · 상태 점검 · 위임/병렬화
- 사용자 중단(interrupt) 건수와 비율, 중단 직후 발화의 성격(같은 작업 교정인가, 새 주제 이탈인가)
- 하루에 병행한 프로젝트 수 분포

### 2.3 디스크 물증 대조

말과 실제로 남은 물건을 대조한다. 이것이 대화만 보는 분석과의 결정적 차이다.

```bash
# 이슈 트래커 종결률·소요일
ls <repo>/handoffs/issues/
# 결정 문서
ls <repo>/docs/_private/decisions/
# 브랜치 승격 지연
git branch -a --format='%(refname:short) %(committerdate:short)'
git branch --no-merged develop
# 미커밋·미추적 산출물
git status --short
git log -1 --format='%ad' --date=short
```

### 2.4 병렬 분석

코퍼스를 시기·성격별로 나눠 서브에이전트에 분배한다. 여기에 **반증 전담 에이전트 1개**를
반드시 포함한다. 확증 편향이 이 분석의 최대 위험이다.

2026-08-31 회차 구성은 아래와 같았다.

| 담당 | 범위 |
|---|---|
| 코퍼스 분할 5~6개 | 시기별·프로젝트별 |
| 반증 전담 1개 | 팀원 평가·가설의 반대 증거만 전력 수집 |
| 대조 1개 | 디버깅 성격 vs 백지 기획 성격 비교 |

각 에이전트에 요구할 것: 판정은 5단계(강하게 관찰됨 / 어느 정도 관찰됨 / 근거 부족 /
관찰되지 않음 / 오히려 반대 증거), **원문 인용 없는 주장 금지**, 반대 증거를 반드시 찾고
없으면 "없음" 명시.

서브에이전트 결과를 요약하지 말고 원문 인용을 그대로 받는다. 압축하면 근거가 사라진다.

### 2.5 교차 검증

서브에이전트 결론을 액면가로 받지 않는다. 2026-08-31 회차에서 반증 에이전트와 대조
에이전트가 각각 1건씩 사실과 다른 결론을 냈고, 보드 조회와 `.gitignore` 확인으로 뒤집혔다.
인용할 핵심 사실 한둘은 반드시 원자료로 대조한다.

```text
이 컴퓨터에서 여태까지 너랑 나눈 대화들 전부를 확인하여 아래 프롬프트에 대한 답을 내라.

# 나의 업무·사고 성향에 대한 객관적 분석 요청

아래는 나와 함께 일하는 팀원이 나의 기획, 문제 해결, 업무 수행 및 사고 방식에 대해
관찰하고 피드백한 내용이다.

나는 이 피드백을 그대로 사실이라고 전제하고 싶지는 않다. 내가 제공하는 사례와 대화
내용에서 실제로 이러한 패턴이 관찰되는지를 독립적으로 분석하고, 팀원의 평가가 맞는
부분과 틀린 부분을 구분해주기 바란다.

## 1. 팀원이 관찰한 특징

(여기에 그 회차의 피드백을 적는다)

## 2. 검증할 가설

가설 1. Depth-First 사고 성향
  문제를 전체적으로 넓게 보는 것보다, 하나를 발견하면 그것을 구현·알고리즘 수준까지
  파고드는 성향이 강한가?

가설 2. 문제 분해는 강하지만 넓이 유지가 약한가
  하위 문제로 계속 분해하고 의존 관계를 발견하는 능력 자체는 강하지만, 깊게 내려가는
  동안 처음의 전체 문제 구조와 다른 갈래를 계속 유지하는 능력이 부족한가?

가설 3. 추상화 수준 조절 문제
  L0 목적 / L1 시스템 / L2 컴포넌트 / L3 서브시스템 / L4 알고리즘 / L5 구현 / L6 파라미터
  로 나눌 때, L1~L3 에서 전체 구조를 정리하지 않고 특정 영역의 L4~L6 으로 빠르게
  내려가는가? 또는 L0 에 머물다 갑자기 L5~L6 으로 이동하는가?

가설 4. 갈래 관리 문제
  새 문제를 발견했을 때 (기록 → 현재 작업 완료 → 우선순위대로 처리) 가 아니라
  (즉시 새 문제로 전환) 하는가?

가설 5. 정지 조건 문제
  "현재 의사결정을 위해서는 이 정도 정보면 충분하다" 보다 "아직 확인하지 않은 부분이
  있으므로 더 알아봐야 한다" 쪽으로 계속 확장하는가?

## 3. 분석 대상 업무

일상생활 사례가 아니라 아래를 중심으로 분석한다.
소프트웨어 개발 · AI Agent 개발 · AI 플랫폼 설계 · 시스템 아키텍처 · RAG · LLM ·
백엔드/프론트엔드 구조 · 인프라 · 데이터 처리 · 장애 분석 및 디버깅 · 기술 기획 ·
요구사항 분석 · 프로젝트 구조 설계.

같은 사고방식이 상황에 따라 장점과 단점으로 어떻게 갈리는지 구분한다.
특히 Depth-First 사고가 트러블슈팅·근본원인 분석·코드 분석에서는 장점이고
아키텍처·기획·요구사항 분석·범위 설정·우선순위 결정에서는 단점으로 작용하는지 본다.

## 4. 반드시 구분해서 볼 것

아래를 한 덩어리로 묶어 평가하지 않는다. 각각 독립적으로 판정한다.

1. 논리적 사고 능력      7. Deep Dive 능력
2. 문제 분해 능력        8. 갈래 관리
3. 문제 구조화 능력      9. 주의 전환
4. 전체 범위 탐색 능력   10. 정지 조건 설정
5. 우선순위 판단         11. 원래 목표 복귀 능력
6. 추상화 수준 조절      12. 계획을 유지하면서 탐색하는 능력

"깊게 파고든다"는 사실만으로 "논리력이 부족하다"고 결론 내리지 않는다.

## 5. 분석 방식

내 설명을 그대로 받아들이거나 나에게 유리하게 해석하지 않는다.
팀원의 평가도 정답으로 가정하지 않는다.
실제 대화와 업무 사례를 근거로 각 가설을 검증한다.

각 특성에 대해 아래 5단계로 판정한다.
  강하게 관찰됨 / 어느 정도 관찰됨 / 근거 부족 / 관찰되지 않음 / 오히려 반대 증거가 있음

반드시 원문 인용을 근거로 붙인다.

## 6. 최종적으로 답할 것

① 팀원의 평가가 얼마나 정확한가
   각 항목에 대해 단순히 맞다/틀리다가 아니라, 관찰된 현상은 맞지만 원인 해석이
   틀렸는지까지 구분한다.

② 사고방식의 핵심 특징 3~5개
   기존 용어에 억지로 맞추지 않는다. 더 적절한 개념이 있으면 그것을 쓴다.

③ 이것은 어떤 종류의 문제인가
   논리력 / 사고 구조화 / 메타인지 / 실행 기능 / 주의 전환 / 우선순위 /
   문제 해결 전략 / 커뮤니케이션 중 어디에 가까운가.
   복합이면 핵심 원인과 파생 현상을 구분한다.
   대화만으로 ADHD 등 의학적 진단을 확정하지 않는다. 그런 가능성을 언급할 경우
   관찰 가능한 행동 패턴과 의학적 진단을 명확히 구분한다.

④ 장점과 약점을 분리
   어떤 업무에서 강력한 장점이고 어떤 업무에서 문제가 되는가.
   Software Engineer / AI Engineer / Agentic AI Platform Engineer 관점에서 평가한다.

⑤ 가장 근본적인 개선 지점
   "계획을 세워라 / 집중해라 / 우선순위를 정해라" 같은 일반론은 피한다.
   아래 흐름 중 어디가 강하고 어디에서 문제가 발생하는지 특정한다.

   문제 정의 → 넓이 파악 → 우선순위 → 깊이 선택 → Deep Dive → 정지 조건
   → 원래 목표 복귀 → 결정

⑥ 최종 프로파일
   현재 사고 방식과 개선된 사고 방식을 나란히 비교한다.
   목적은 Deep Dive 및 기술 분석 능력을 없애는 것이 아니라, 그 장점은 유지하면서
   기획·아키텍처·업무 관리에서 발생하는 약점을 보완하는 것이다.

멀티에이전트를 사용해서 처리하라.
```

## 4. 이 분석의 한계

회차마다 결과 앞에 명시한다.

1. **대화 기록은 AI 와의 1:1 대화뿐이다.** 사람 팀원과의 회의·구두 대화는 없다.
   팀원이 본 장면과 기록에 남은 장면이 애초에 다를 수 있다.
2. **AI 상대로는 탐색이 싸다.** "일단 물어보고 아니면 만다"의 비용이 낮아, 사람 상대보다
   산만해 보이는 편향이 있다.
3. **기간이 짧다.** 로그가 남아 있는 구간만 본다. 그 전은 알 수 없다.
4. **디스크 물증이 대화보다 강한 증거다.** 말은 의도이고 파일은 결과다. 둘이 어긋나면
   파일을 믿는다.
