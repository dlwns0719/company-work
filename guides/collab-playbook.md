# collab-playbook — 타팀 협업 지침

## 목적

세 가지를 한다.

1. **내 습관 교정** — 타팀 공유 문서를 만들 때 반복되는 내 문제점(P1~P7)을 사전에 막는다.
2. **상대 유형 판정과 대응** — 회의록·대화를 근거로 상대 유형을 판정하고, 유형별 대응 전략을 적용한다.
3. **프로파일 축적** — 새 사람·새 미팅이 생기면 같은 형식으로 유형과 대응을 추가한다.

기준 문서는 `collab-playbook/playbook.md` (핵심 원칙·프로파일 인덱스·유형 코드).

## 발동 조건

슬래시 커맨드가 없어도 아래 상황이면 이 가이드를 적용한다(`GUIDE.md` 는 자연어로 가장 적합한 행을 추론한다).

- 타팀에 공유할 README·운영 계약서·요구사항 문서·회의 자료를 쓰거나 검토한다
- 회의 녹취록·회의록을 분석해 상대의 요구와 의도를 파악한다
- 상대의 협업 유형을 판정하거나 대응 방식을 정한다
- "주도권", "선 긋기", "어디까지 공유해야 하나", "이 사람 왜 이러나" 같은 고민이 나온다

## 입력

`$ARGUMENTS` = `[모드] [대상]`. 모드가 없으면 대상을 보고 Step 2 에서 추론한다.

| 모드 | 대상 | 하는 일 |
|---|---|---|
| `doc` | 문서 경로 또는 작성 요청 | 타팀 공유 문서 작성·검토 |
| `meeting` | 회의록·녹취 경로 또는 붙여넣은 본문 | 회의록 분석 + 프로파일 갱신 |
| `respond` | 인물 식별자 + 상황 | 대응 방식 제안 |
| `profile` | 인물 식별자 | 새 프로파일 추가 |

## 파일 지도

| 상황 | 읽을 파일 |
|---|---|
| 타팀에 줄 문서를 쓰거나 검토한다 | `collab-playbook/self-profile.md` → `collab-playbook/doc-checklist.md` |
| 회의록·녹취록을 분석한다 | `collab-playbook/meeting-analysis.md` → 해당 인물의 `collab-playbook/profiles/*.md` (있으면) |
| 특정 사람에게 어떻게 대응할지 정한다 | `collab-playbook/profiles/<식별자>.md`. 없으면 `collab-playbook/profiles/_template.md` 로 새로 만든다 |
| 새 사람을 프로파일에 추가한다 | `collab-playbook/meeting-analysis.md` §4 프로파일 작성 절차 → `_template.md` 복사 |

## Step

### Step 1 — 기준 로드

1. `collab-playbook/playbook.md` 를 Read 로 읽는다(원칙 §2, 프로파일 인덱스 §3, 유형 코드 §4).
2. 대상 인물이 특정되면 인덱스에서 프로파일 파일을 찾아 Read 로 읽는다.

### Step 2 — 모드 판정

인자 또는 요청 내용으로 `doc` / `meeting` / `respond` / `profile` 중 하나를 정하고, 무엇을 할지
사용자에게 1줄로 밝힌다. 두 모드가 겹치면(예: 회의록을 분석하고 대응도 정한다) `meeting` → `respond` 순으로 이어서 한다.

### Step 3 — 모드별 실행

**`doc` — 문서 작성·검토**

1. `self-profile.md` 를 읽고 이번 문서에서 재발하기 쉬운 항목(P1~P7)을 골라 밝힌다.
2. `doc-checklist.md` §1 구조 템플릿으로 초안을 만들거나, 검토라면 기존 문서를 템플릿과 대조한다.
   각 절에 `[우리 결정]` / `[인프라 재량]` / `[합의 필요]` 표기를 붙인다(§2).
3. 수신자 프로파일이 있으면 "이 사람에게 문서를 줄 때" 절의 먼저 볼 것·걸고넘어질 것·빼야 할 것을 반영한다.
4. `doc-checklist.md` §4 공유 전 검증 체크리스트와 §5 "상대가 반드시 물어볼 8가지" 를 돌려,
   즉답 못 하는 항목을 목록으로 보고한다. 하나라도 있으면 "아직 공유 준비가 안 됐다" 고 판정한다.

**`meeting` — 회의록 분석**

1. `meeting-analysis.md` §1 출력 형식 7개 절을 **빠짐없이** 채운다. 5번(내 쪽 문제)과 7번(사용자
   우려가 과잉인지 과소인지 판정)을 빼면 분석이 반쪽이다.
2. 근거는 회의록 원문 근처 표현으로 인용한다. 녹취에 없는 발언을 지어내지 않는다.
3. 기존 프로파일과 대조해 유형을 확정하거나 갱신한다. 새 인물이면 `profile` 모드로 이어간다.
4. 내 쪽 문제 포인트가 `self-profile.md` 의 기존 패턴이면 관측 횟수 증가를, 새 패턴이면 P8 이후 추가를 제안한다.

**`respond` — 대응 방식**

1. 해당 프로파일의 "대응 전략"(지켜야 할 선 / 내줘도 되는 것 / 먼저 제안할 문장)을 그대로 적용한다.
2. 사용자가 상대를 과잉 해석하는지(예: 표준 요구를 주도권 침해로 읽음), 과소 해석하는지
   `meeting-analysis.md` §3 기준으로 **대목을 특정해** 판정한다. 사용자 편을 들기 위해 판정을 흐리지 않는다.

**`profile` — 새 인물 추가**

`meeting-analysis.md` §4 절차를 따른다. 실명 대신 `<역할>-<식별자>` (예: `infra-architect-A`) 로 파일명을 쓴다.
같은 인물과의 두 번째 회의부터는 새로 만들지 않고 "관측 이력" 에 일자와 변화만 추가한다.

### Step 4 — 파일 갱신 (승인 후)

`self-profile.md` 관측 횟수·새 패턴, 프로파일 신설·관측 이력, `playbook.md` §3 인덱스·§4 유형 코드는
**제안 내용을 먼저 보이고 사용자 승인 후** 쓴다. 분석 결과만 원하는 요청이면 파일은 건드리지 않는다.

## 보고 전

`guides/GUIDE_CORE.md` §5 Self-Check 를 출력한다.

## 금지

- 회의록에 없는 발언을 인용하거나 유형 근거로 쓰지 않는다.
- 프로파일 파일명·본문에 실명을 쓰지 않는다. 역할+식별자만 쓴다.
- 분석에서 "내 쪽 문제"(§1-5)와 "과잉/과소 판정"(§1-7)을 생략하지 않는다.
- 사용자 편을 들려고 판정을 흐리지 않는다.
- 승인 없이 기준·프로파일 파일을 고치지 않는다.
