# Doc Checklist — 타팀 공유 문서 작성 지침

## 1. 문서 구조 템플릿 (README / 운영 계약서)

상대가 제일 궁금한 순서로 배치한다. 오픈소스 README 관례를 따른다. "내부 흐름"은 뒤로 보내거나 링크로 뺀다.

```
# <이름>
한 문단: 이것이 무엇이고, 누가, 왜 쓰는가. (P5 목적 세 문장)

## 빠른 시작
- 빌드: 명령 한 줄, 필요한 build-arg
- 실행: 명령 한 줄, 인자 없음이면 "인자 없음"이라고 명시
- 로컬 세팅: 언어·런타임 버전, 의존성 설치, 최소 환경변수

## 설정
- 환경변수 표: 변수 / 값 예시 / 역할 / 필수 여부 / 주입 주체(이미지 내장 · ConfigMap · Secret)
- 프로파일이 있으면 프로파일별 차이

## 외부 연동 (경계 — 반드시 정확히)
표: 대상 / 프로토콜 / 인증 방식 / 최소 권한 범위 / 대상 범위 결정 기준 / 코드 위치
- 현재 지원하는 인증 방식과 지원하지 않는 방식을 모두 적는다.
- 개인 계정·개인 토큰이 끼어 있으면 그 사실과 교체 계획을 적는다.

## 운영 시 제약 (경계 — 합의 대상)
- 동시 실행 가능 여부와 이유
- 상태 유지 여부(볼륨·DB), 필요한 쓰기 권한
- 종료 코드·로그 위치·정상 판정 기준
- 실측 수치(소요 시간, 메모리, CPU) — "요구"가 아니라 "측정값"으로

## 범위 밖 / 인프라 재량
스케줄러 종류, 주기, 재시도, 알림 채널, CI/CD 구성 등은 "인프라 담당 재량"으로 명시하고,
우리가 원하는 값이 있으면 "희망값 + 이유"로 적는다.

## 부록: 내부 동작 (관심 있는 사람용)
단계별 흐름, 산출물, 캐시 전략 등. 여기는 길어도 된다.
```

## 2. 영역 분리 표기 규칙

각 절 제목 옆이나 첫 줄에 소유를 표시한다.

- `[우리 결정]` — 개발팀이 정한 것. 상대가 바꾸려면 우리와 합의.
- `[인프라 재량]` — 상대가 정할 것. 우리는 희망값과 이유만.
- `[합의 필요]` — 양쪽이 맞춰야 할 것. 미팅 안건으로 올린다.

이렇게 표시하면 상대가 "왜 이걸 여기서 정하냐"는 반응 대신 "이건 우리가 정하면 되겠네"로 읽는다.

## 3. 첫 전달 규칙 (P4)

- 첫 전달은 **한 장 개요**로: 무엇 / 왜 / 지금 상대에게 필요한 것 3개 이내 / 본문 링크.
- 문서가 여러 개면 읽는 순서와 각 문서의 목적을 한 줄씩.
- 가능하면 문서 전달 전에 10분 구두 설명. 설명 없이 던지면 상대는 "정체 확인" 미팅을 잡는다.

## 4. 공유 전 검증 체크리스트 (P3)

문서의 모든 절에 대해:
- [ ] 내가 이 항목을 왜 적었는지 말할 수 있다
- [ ] 명령·절차는 실제로 실행해 봤다 (안 해봤으면 "미검증" 표시 또는 삭제)
- [ ] 수치는 측정 근거(일자, 조건)가 있다
- [ ] 외부 연동 표의 인증 방식·권한 범위는 코드를 직접 읽고 확인했다
- [ ] 상대 영역 항목이 확정값처럼 적혀 있지 않다
- [ ] 테스트 절이 있으면 CI(러너, 외부 의존 없음)용과 배포 후 검증용을 분리했다
- [ ] "알려진 한계"(실패하는 테스트, 미이관 기능)는 숨기지 않고 적었다

## 5. 상대가 반드시 물어볼 것 (미리 답을 넣어라)

인프라·아키 유형이 첫 미팅에서 거의 항상 묻는 것:
1. 외부에 어떻게 연결하나 (인증 방식, 계정 주체, 권한 범위)
2. 대상 범위를 무엇으로 결정하나 (목록 파일? 자동 필터? 누가 관리?)
3. 실행 명령이 뭐냐, 인자는 있나
4. 상태를 어디에 두나, 동시 실행하면 어떻게 되나
5. 정상·실패를 뭘로 판단하나 (종료 코드, 로그, 알림)
6. 이걸 하면 뭐가 좋아지나 (목적)
7. 다음 단계는 뭔가 (형상이 바뀔 예정인가)
8. 언제까지 필요한가

8개에 즉답을 못 하는 항목이 있으면 그 문서는 아직 공유 준비가 안 된 것이다.
